## 這個區塊要解決什麼

1. 「新增運動紀錄」裡的訓練項目明細目前是純自由文字，沒有資料庫背書、無法自動完成、也沒有驗證。
2. 目前只能一次記一天的運動，沒有「規劃未來 3～5 天訓練分割、排到月曆上，之後再回來補實際紀錄」這種計畫型工作流程。

詳細設計、資料表結構、API 規格、前端整合方式，全部寫在 **[BLOCK_8_ARCHITECTURE_DESIGN.md](BLOCK_8_ARCHITECTURE_DESIGN.md)**，這是本區塊唯一、也是最重要的文件。

---

## 已確認的 3 個設計決策

開發前你已經拍板，實作時直接照做即可，不用再確認：

1. ✅ 瑜珈/拉伸也做動作庫（`yoga_stretch_items`，比照健身動作庫）
2. ✅ 動作庫全體共用一份，但依「個人使用頻率」提升該使用者的搜尋排序（不是每人各自一份庫）
3. ✅ 自訂動作預設**手動**加入庫（使用者按「加入動作庫」才會存），不自動加入

（第 3 點如果你實際開發時想改成自動加入，設計文件裡有註明怎麼改，影響範圍很小。）

## 這個區塊跟其他區塊的關係

- **依賴**區塊 2（`workout_templates`/`template_details`，多天計畫的「一天」就是重用這個既有模板結構）與區塊 7（訓練項目明細表單、範本快速填寫的 UI 已經做好，動作庫的自動完成是加在這些既有元件上）。
- **不會**動到區塊 1 的 `schema.sql` 既有表格定義以外的地方——只新增表，沒有修改或刪除既有欄位（`exercise_details`/`template_details` 是新增可為空的欄位，不影響既有資料）。
- 目前整個專案（區塊 2）還是**純記憶體儲存**，沒有真的接上區塊 1 的 SQLite。區塊 8 的設計文件裡對這點有specific的因應方式（短期先用記憶體 dict、長期 API 合約不變直接換成真資料庫），開發時不用等專案先把資料庫接上才能動工。
